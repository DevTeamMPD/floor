## 1. สรุปสำหรับผู้บริหาร

สะพานเชื่อมสองระบบ **ออกแบบมาถูกและทำงานได้** — มี outbox กันงานหาย มีลายเซ็นกันปลอม มี `ext_ref` กันจองซ้ำ และยืนยันแล้วว่าไม่มีโค้ดฝั่งไหนแอบแตะตารางของอีกฝั่ง

แต่พอดูตัวเลขการใช้งานจริง เจอเรื่องที่สำคัญกว่าจุดบกพร่องทางเทคนิค: **งานติดตั้ง 139 งานในระบบ มีแค่ 14 งาน (10%) ที่มาจาก CRM** ที่เหลือ 90% เข้ามาทางอื่น แปลว่าสะพานนี้ยังไม่ได้เป็นทางหลักของธุรกิจ

ดังนั้นแผนนี้แบ่งเป็นสองส่วน — **ซ่อมสิ่งที่กระทบเงินทันที** (C0–C4, 3.5 วัน) และ **คำถามที่ต้องตอบก่อนลงทุนเพิ่ม** (C7) ส่วนงานสถาปัตยกรรมเต็มรูปแบบ (C5) ถูกเลื่อนไว้อย่างตั้งใจ เพราะยังไม่คุ้มกับปริมาณงานที่วิ่งผ่านจริง

## 3. ข้อค้นพบที่เปลี่ยนลำดับความสำคัญ

### F-1 · CRM ไม่เคยรู้ว่างานติดตั้งจบ
FloorNow มีทางยิงกลับเข้า CRM อยู่ทางเดียวคือข้อความในตั๋ว ไม่มีเส้นทางใดบอกกลับว่า "ติดตั้งเสร็จ" หรือ "ลูกค้าเซ็นรับงาน" สถานะสุดท้ายที่ CRM รู้จักคือ **ลงคิวงานแล้ว**

นี่คือสาเหตุเชิงระบบที่ `warranties_bbps` เป็นศูนย์ และรายรับขาดไป 3 เดือน — ไม่มีสัญญาณบอกว่าถึงเวลาต้องทำ ไม่ใช่ปัญหาวินัยของคน

### F-2 · แต่ผลกระทบจำกัดอยู่ที่ 14 งาน
เพราะสะพานนี้รับงานแค่ 10% การซ่อมทางกลับจะแก้ได้เฉพาะงานที่มาจาก CRM ส่วนอีก 125 งานยังไม่มีใครกระตุ้นให้บันทึกรายรับอยู่ดี
→ ทางแก้ที่ให้ผลจริงจึงต้อง **ครอบคลุมงานทุกแหล่ง ไม่ใช่เฉพาะงานที่มาจาก CRM** (ดู C3)

### F-3 · ความเสี่ยง "ข้อความค้าง" ยังไม่เกิด
ผมเคยจัดให้เป็นระดับกลาง แต่ข้อมูลจริงบอกว่าค้าง 0 จาก 60 ข้อความ
→ ลดเป็นงานป้องกัน (C4) ไม่ใช่งานเร่งด่วน

### F-4 · สถานะงานเป็นข้อความไทยที่ไม่ได้ควบคุม
พบ 16 ค่าที่ต่างกัน และมี `เสร็จสิ้น` (12) กับ `done` (10) ปนกันอยู่ ทุกสูตรที่นับ "งานที่เสร็จแล้ว" ต้องจำสองค่านี้ ถ้ามีคนพิมพ์ค่าใหม่ ตัวเลขจะเพี้ยนเงียบ ๆ

### C2 · ปิดเคส 6 เหตุการณ์ตายค้าง — 0.5 วัน

**ตรวจแล้วพบว่า** ทั้ง 6 งานมีนัดหมายอยู่ใน FloorNow เรียบร้อยแล้ว — **ห้ามยิงซ้ำ** เพราะจะได้นัดซ้อน

**ทำ**
1. ตรวจ 2 งานที่มีนัด 2 รายการ ว่าเป็นการจองซ้ำหรือเป็นงานสองวันจริง — ให้หัวหน้าช่างยืนยัน

update public.outbox_events

**เกณฑ์ผ่าน** ไม่มีเหตุการณ์สถานะ `dead` ที่ยังไม่มีคำอธิบาย

### C3 · แจ้งเตือนงานที่ติดตั้งเสร็จ — 1.5 วัน · **ให้ผลทางธุรกิจสูงสุด**

**แก้ปัญหาอะไร** F-1 และ F-2 — ทำให้มีคนรู้ว่าถึงเวลาลงทะเบียนรับประกันและบันทึกรายรับ **สำหรับงานทุกแหล่ง ไม่ใช่เฉพาะงานที่มาจาก CRM**

**แนวทาง** ใช้รูปแบบเดียวกับที่ตกลงไว้กับ HR — อ่านข้ามระบบผ่านวิวในสคีมาที่ตั้งชื่อไว้ ไม่ใช่การแตะตารางกันตรง ๆ

```sql
create schema if not exists crm_read;

create or replace view crm_read.completed_installations as
select j.job_no,
       j.order_no,
       j.external_id            as bbps_production_id,
       j.source,
       j.customer_name,
       j.completed_date,
       j.closed_at,
       j.status
from public.install_jobs j
where j.status in ('เสร็จสิ้น', 'done');
```

จากนั้นเพิ่ม cron ฝั่ง CRM `/api/cron/installations-completed` (รายวัน 07:00) ที่:
1. อ่าน `crm_read.completed_installations` เฉพาะงานที่ปิดใน 7 วันล่าสุด
2. สร้างรายการรับประกันแบบร่างใน `warranties_bbps` ถ้ายังไม่มี
3. สร้างงานค้างให้ฝ่ายบัญชี "บันทึกรายรับของงานนี้" ถ้ายังไม่มีรายการใน `revenue_bbps`
4. ผลลัพธ์ทั้งหมดขึ้นบนแบนเนอร์เดียวกับ C0

**เกณฑ์ผ่าน**
- [ ] รันย้อนหลัง 90 วันแล้วสร้างรายการรับประกันแบบร่างได้ครบทุกงานที่ปิดแล้ว
- [ ] ไม่สร้างซ้ำเมื่อรันสองรอบ (ทดสอบด้วยการรันติดกัน)
- [ ] งานจากทั้ง 3 แหล่ง (`bbps` · `sales_txn` · `floor_direct`) ถูกจับได้เหมือนกัน

**ย้อนกลับ** ปิด cron และ `drop schema crm_read cascade;` — ไม่มีการแก้ข้อมูลเดิม รายการที่สร้างเป็นร่างทั้งหมด

### C4 · cron ผลักข้อความที่ค้าง — 0.5 วัน (งานป้องกัน)

**เกณฑ์ผ่าน** จงใจสร้างข้อความค้างในระบบทดสอบ แล้วยืนยันว่าถูกผลักออกภายใน 15 นาทีโดยไม่ต้องเปิดหน้าแชท

### C6 · คุมค่าสถานะงาน — 0.5 วัน

**ทำ** รวม `done` เข้ากับ `เสร็จสิ้น` ให้เหลือค่าเดียว แล้วใส่ `check constraint` หรือตารางอ้างอิงสถานะ

```sql
-- ขั้นที่ 1 รวมค่าที่ซ้ำความหมาย
update public.install_jobs set status = 'เสร็จสิ้น' where status = 'done';

-- ขั้นที่ 2 ล็อกไม่ให้มีค่าใหม่หลุดเข้ามา (ใส่หลังยืนยันรายการค่าที่ถูกต้องกับหัวหน้าช่าง)
-- alter table public.install_jobs
--   add constraint install_jobs_status_check check (status in (...));
```

**ก่อนรัน** ต้องไล่โค้ดทั้งสอง repo ว่าไม่มีที่ไหนเทียบกับสตริง `'done'` ตรง ๆ

**เกณฑ์ผ่าน** ค่า `status` ทั้งหมดอยู่ในรายการที่ตกลงกันไว้ · รายงานทุกตัวให้ตัวเลขเท่าเดิมหลังรวมค่า

### C7 · คำถามธุรกิจ — ไม่ใช่งานเขียนโค้ด

**ทำไมงานติดตั้ง 90% ไม่ผ่าน CRM**

เราลงทุนสร้างสะพานที่ออกแบบมาดี แต่มันรับงานแค่ 10% ก่อนจะลงทุนกับ C5 หรืองานสถาปัตยกรรมอื่นใด ต้องตอบให้ได้ก่อนว่าตั้งใจให้เป็นแบบนี้หรือเปล่า

| ถ้าคำตอบคือ | แปลว่า |
|---|---|
| ตั้งใจ — `sales_txn` คือทางหลักของธุรกิจ | สะพาน CRM เป็นทางรอง ไม่ต้องลงทุนเพิ่ม · เอาแรงไปทำให้ `sales_txn` แข็งแรงแทน |
| ไม่ตั้งใจ — CRM ควรเป็นประตูหน้า | ต้องหาว่าอะไรทำให้คนเลี่ยงไปใช้ทางอื่น แล้วแก้ตรงนั้นก่อน · การซ่อมสะพานไม่ช่วยถ้าไม่มีใครเดินข้าม |

**ผู้ตัดสิน** ผู้บริหาร + หัวหน้าฝ่ายขาย · **ควรตอบภายใน** ก่อนวางแผนไตรมาสถัดไป

## 6. หลักการที่ตั้งไว้จากงานรอบนี้

ให้ใช้เป็นกติกากับการเชื่อมต่อข้ามระบบทุกครั้งต่อจากนี้

1. **อ่านข้ามระบบ** ผ่านวิวในสคีมาที่ตั้งชื่อไว้เท่านั้น (`crm_read` · `hr_read`) ห้ามโค้ดของระบบหนึ่งเรียกตารางของอีกระบบตรง ๆ แม้จะอยู่ในฐานข้อมูลเดียวกัน
2. **เขียนหรือกระตุ้นข้ามระบบ** ผ่าน outbox event เท่านั้น ห้ามเขียนตารางของอีกฝั่ง
3. **ทุกเหตุการณ์ต้องมีกุญแจกันซ้ำ** และปลายทางต้องตอบ `409` ได้อย่างปลอดภัย
4. **ทุกงานตามเวลาต้องมี run log และต้องอยู่ใน heartbeat** ที่ C0 วางไว้ — งานที่ไม่มีใครเฝ้า ถือว่าไม่มีอยู่จริง
5. **ค่าคงที่เชิงสถานะต้องถูกควบคุม** ห้ามใช้ข้อความอิสระเป็นเงื่อนไขของตรรกะ
